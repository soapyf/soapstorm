## 1. The layer model

Atmo Magic is a **layer over an untouched stock viewer, not a fork of it**. The whole system compiles out of the shading path with one define, and the master rule that governs every shared file is stated at `llviewershadermgr.cpp:300`: any Atmo-era change to SHARED shading — the sky, the dome clouds, the atmospheric module, the water shaders — lives behind `#ifdef SS_ATMO` with the stock line in `#else`, so **with the system off every stock shader compiles byte-for-byte pristine**. The define is injected by `add_common_permutations` only while the `SSAtmoEnabled` setting is on; the listener registered at `llviewercontrol.cpp:1401` (`handleSetShaderChanged`) rebuilds shaders on toggle, so the cost is compile-time and there is none at runtime either way. Runtime nuance — weather active versus idle, this track versus that one — stays **uniform-driven inside the variant block**. The define is only the master pristine/modified split and must never be asked to carry a runtime state.

The same split runs on the CPU: **every CPU twin of shader math gates on the same `SSAtmoEnabled` `LLCachedControl`**, at `lldrawpoolwlsky.cpp:123`, `llvosky.cpp:1087`, `ssatmoenvapplier.cpp:185` and `ssatmomagic.cpp:119`. A CPU-side calculation that mirrors a shader block and does not gate on that setting is a defect, because it means the two halves of the fork can be in different states at the same instant.

**What is shared, wholesale and unmodified.** The stock EEP/windlight sky equations (`doc/eep_atmosphere_reference.md`: "Stock math is pristine in this fork (SS_ATMO touches none of it)" — the reference document exists so presets are authored against the real equations instead of folklore). The deferred G-buffer, the lighting pass and SSAO. The whole glow chain — `renderFinalize`, tonemap/gammaCorrect, `generateGlow`, `combineGlow`, the `mGlow` ping-pong. The EEP LLSD serialisation keys, which "must not drift" even where the UI name has deliberately diverged from the storage name (`mSkyMoistureLevel` on screen, `moisture_level` on disk). And the entire water machinery: `LLVOWater::updateGeometry`, the `PARTITION_WATER`/`PARTITION_VOIDWATER` partitions, `POOL_WATER`, the water shaders, water haze, refraction, the exclusion mask, **and the stock pcodes**, so every pcode-keyed check in the viewer treats Atmo water and stock water identically with nothing registered anywhere. `LLVOWater::mIsAtmoWater` is the only discriminator. Because the pcodes are shared the pcode factory cannot build the subclasses, so `SSWaterWorld` news them directly and hands them to `gObjectList.adoptViewerObject`.

**What is replaced.** The water plane *geometry* only (`SSWater` / `SSEdgeWater` / `SSFarWater` instead of bending `LLVOWater`/`LLVOVoidWater`; stock void water's nine stretched slabs replaced by a 256 m tile grid). Optics under an active Atmo environment (`skyF.glsl` renders `ssOptics` procedurally; **idle viewers still get the stock `halo_map` bit for bit**). The sun-position gate for optics (`SSAtmoEnvApplier::sunRiseFraction` replaces the stock centre-crossing test, which popped halos at centre-rise). The info-view dim (section 8).

**What is hijacked rather than replaced**, which is a third category and the one with the sharpest rule: the region water height store. The region water object doubles as `LLSurface`'s height store, so **it must never be killed** — suppression is at the two draw call sites, not at object lifecycle. Originals are captured at first hijack and put back on deactivate; an external write is recognised because it is the one height on the region that is not the one we wrote, so deactivating never clobbers the sim's latest word. Exactly one water family renders on any given frame, and `LLDrawPoolWater::pushWaterPlanes` plus the `pushFaceGeometry` override are stated to be the **complete** set of render entry points because both families share one `mDrawFace` list in the single water pool.

**Where the fork's own code lives**: `indra/newview/ss*.{h,cpp}`, registered in `CMakeLists.txt` beside the `fsrezqueue` entries. Injections into stock files are wrapped in `<SS:Nexii>` tags. `doc/archive/` is marked out of date and is good for intent only — code plus the `[interaction: X]` tags is the current truth.

## 2. The container and its operators

**The architecture decision (user, 2026-09-06, `doc/atmo_magic_phase8_show.md` §4·0):** the volumetric field is the **medium** — a deterministic fabric of puffs, a pure function of (air-frame position, seed, weather, cycle time). **Entities do not replace it; they act on it.** Everything an entity does is one of four operator kinds, all evaluated per frame in closed form, never integrated:

| kind | what it does |
|---|---|
| **displacement** `D(p, t)` | moves the fabric — puffs, and every observer's read of the field — by a bounded closed-form offset |
| **density / occupancy** | modulates presence, tower, anvil, drive, coverage over an area |
| **emission** | adds geometry the fabric has no cell for |
| **shading** | changes how the fabric is lit or coloured locally |

Lesson 51 makes the classification mandatory rather than descriptive: **classify every new weather feature as one of the four operators before designing it, because the rules come with the class.** Those rules are:

1. **Purity.** Every operator is a pure function of world state and cycle time — never of camera, settings or frame time.
2. **Boundedness.** Displacements are bounded in *displacement*, not merely in rate (lesson 10; see §3 for why a rate clamp is not a bound).
3. **Replication at every field read.** The operator set per frame is a small fixed-size list — the uniform slot arrays — so that the fragment gate, the shadow bake and `precipNoiseAt` read the *same* operators the builder applied. `SSStormCouple::MAX_CELLS = 4`, and the slots are filled hero-first then by distance to the weather-domain anchor, never by camera distance.
4. **Composition order is fixed, and observers invert in reverse.** The producer applies hero shift, then swirl, then tornado pull, then O(z); observers undo O(z), then tornado, then swirl, then hero. This is lesson 12 generalised.
5. **A twin is owed wherever an operator is replicated** (§4).

**The operators that exist today**, by kind:

*Displacement.* The hero storm's local frame shift `S` (`SSDeckFrame::heroShift`), bounded at `min(HERO_SHIFT_RADIUS_FRAC × radius, HERO_SHIFT_CAP_M)` = `min(0.15 r, 390 m)`, about 1.5 cells; with `RADIUS_MAX_M` 2200 the radius term (330 m) binds first, so the absolute cap only guards a future radius change and `HERO_SHIFT_CAP_M = 0` disables the slide outright. The wind profile's shear lean `O(z)`, bounded at `SSWindProfile::SHEAR_CAP_M = 2500 m` (about 10 × `CELL_M`). The virga curtain's wind-fall skew (`SSVirga::skewOffsetM`, slope-capped at `SKEW_RATE_MAX` = never steeper than 45° off vertical, then magnitude-capped at `SKEW_CAP_M` = 900 m). The sub-puff jitter `placeWorld`'s caller adds, up to `0.4 × CELL_M` on each axis. And the Tier B body jitter (`SSDeckMacro::bodyJitterM`, a hashed offset on a **disc** of radius `MACRO_JITTER_FRAC × MACRO_M` = 156 m) — which is an LOD-scope displacement, hashed per block and world-state-free, so it moves the one body and never adds a second. *Coming:* the supercell swirl, the tornado's swirl/inward/downward pull, the shelf's lift.

*Density / occupancy.* The storm coupling's per-cell tower window and anvil (`SSStormCouple`; `STORM_TOWER_LO/HI` = 0.12/0.60), with the **delegation rule** attached: at the weathers that spawn cells the deck-wide consolidation ramp already saturates the tower window, so while any cell is active the deck-wide figure becomes `storm × 0.5` (`SSStormCouple::deckConsolidation`) and the cells carry the rest — the sky outside cells is *less* consolidated than before, which is exactly what makes discrete storms read. The squall line band (`SSSquall::applyLineBand`, `ss_line_*` uniforms) carrying wall and shelf, on a lifecycle envelope of 0 at birth, 0.999 at age 0.42, 0 at death. Precipitation intensity and shaft drive (`precip × presence`, gated at `SSVirga::THRESHOLD` = 0.18). The overshoot lid `lidTopM(top_z, thickness, overshoot)`, mirrored in GLSL and sampled at the same quantised cell so the lid rises only where the puff was lifted. *Coming:* kilometre-wide rain-cloud footprint entities and the anatomy tier's analytic carves.

*Emission.* Rain shaft cards (`SSVirga`), emitted **into `mPuffs` itself** so the existing farthest-first painter's sort interleaves them correctly, flagged on the spare `b` vertex channel (`b == 1`). The funnel's collar quads (`SSVortex`, `COLLARS` = 14 per funnel, `MAX_ACTIVE` = 3), which have their own program and **never enter `mPuffs` or the puff budget**. Tier B macro bodies (`SSDeckMacro`, one per occupied 520 m block). The base veil's sheet quads (`SSVeil`, 5,764 under one partitioned loop). *Coming:* the anatomy parts — anvil sheet, mammatus lobes, wall and tail cloud, flanking line.

*Shading.* Meso gloom, applied as `gloom *= 1 − 0.35 · sample.meso` in the **one shared lighting tail** for both the puff and the veil paths, from the quantised storm sample the fragment stage already holds — which is why no vertex channel was ever needed for it and why the spare `b` channel was free for the shafts. The veil's underside form (`SSDeckShade` with the veil's fixed representative depths: `facingUp` 0.15, `aboveDepth` 0.65, `belowDepth` 0.65, `coreness` 1, `rim` 0, and `VEIL_DEPTH` 0.65). The lighting variants behind `SSAtmoCloudLightVariant` — 0 today's tail, 1 POWDER, 2 HG2, 3 FULL — all dormant at the default 0.

**One classification is genuinely open and is recorded rather than resolved:** the base veil is emission (its quads) *and* shading (its form), and §4·0's table lists only "the veil underside form" under shading. The sheet's geometry has no home in the four-kind taxonomy. Likewise the deck's output response (`ss_soft_clip_unit`) is container-level lighting rather than an operator on the container; it is treated as such in §6.

**LOD is not an operator.** `ssdecklodcore.h` states the boundary in its own header: LOD is a function of CAMERA DISTANCE ONLY and touches render decisions only — which sub-puffs are placed, their alpha, the walk's extent — **never the field**. The `ssveilcore.h` law rests on exactly this split: the veil *keeps* the sky's genuine geography (the coverage gate's bilinearly softened holes, because a hole in the deck must stay a hole all the way through) and *drops* the deck's rendering economy (the far thinning and the puffs' edge fade, because those are camera-distance decisions about how many bodies to draw, not statements about where cloud exists). The old veil law multiplied itself by a render decision; the new one inverts that decision instead — `rimIn(d) = 1 − keepNorm(keepFrac(d)) · edgeFade(d)`, the exact complement of the share of rim presence the puffs still draw, so `rimIn + puffRimShare == 1` identically.

## 3. Coordinate and frame rules

**Three frames, and content belongs to exactly one.** The **world frame** holds everything positional that must agree between clients: storm cells, meso centres, tornado touchdowns, the funnel's contact point. Motion in it is closed-form — `centre(t) = origin + v · age` — because an integrator makes storm positions a function of session history and framerate, and two avatars would then see the same tornado at different coordinates. The **air frame** is the drifted fabric; nothing positional may ever live there, and the cross-client divergence of the drift accumulator's session-start seeding is accepted debt *for the shapeless cloud pattern only*. The **track frame** carries authored heights: the water plane and both decks' bases are metres relative to `SSAtmoEnvTrack::mFloorZ`, negative below it, and the renderers' resolvers add the floor back where they render.

**One integrator, at deck-base altitude, in F64.** Every other altitude is a **bounded closed-form offset**, never a second accumulator. Two free-running accumulators at different velocities diverge without limit and their independent 1e6-m wraps snap the difference — rejected on the design review, 2026-09-05. The drift wrap is on `lcmSpanM` = 800800 m, the lcm of every air.xy period (cell 260, `SS_NOISE_M` 880, `SS_SKEW_M` 1400, both decks' cell-quantised noise tiles at 2080); `fmodf(drift, 1e6)` was not a multiple of any of them and already repopped the field.

**The producer/observer rule** (`ssdeckframecore.h`, corrected after the phase-4 opus review found the first contract unsound). The CPU builder is the **producer**: for lattice cell `c` it evaluates `S` at the *unshifted* centre, reads the pattern (gate hash, presence, `n_map`) at the plain centre `c`, and places the puff at `placeWorld = c + drift + S + O(z_puff)`. The fragment stage, the shadow bake and `precipNoiseAt` are **observers** of a world point: `air = world − drift`, and they read *everything* at `frameAir(air, z) = air − S − O(z)`. Lesson 12 states the general form: **one coordinate per observer, derived from the producer's placement by inversion** — never a split where some reads undo a transform and others do not, and the round trip (place, observe, land on the producer's cell) is written as a twin test *before* the call sites.

Three consequences that are easy to get wrong and have each been got wrong once:

- **Base-anchored observers.** The veil sheet, the shadow bake and `precipNoiseAt` are base-anchored *by definition* and read at `gateAir = air − S`, never evaluating `O(z)` at all. Stating this as "O(z0) == 0 so it reduces" was **wrong** for the sheet: it is drawn 46–106 m above the base and a storm profile already carries 90–210 m of `O` there.
- **Observer quantisation removes O first.** The observer's storm sample / hero influence is quantised from `air − O(z)`, because `O` does not depend on influence; quantising from the *leaned* air would put a high-altitude puff's sample up to 2.5 km from its producer cell and outside the hero entirely.
- **The bake has two loops with two roles.** Its cell loop is a producer mirror (plain-centre read for the plain hashed index); its texel loop is an observer for *every* read, with the occupancy grid padded by the cap's worth of cells. Every observer derives `S` in ONE step from its own quantised cell; a two-step fixed point that no other observer ran was the phase-4d review's single blocking item.

**The quantised producer-cell rule (the lockstep).** The CPU samples the storm field once per 260 m cell **at the cell centre**, and the fragment stage and `precipNoiseAt` sample at the *same* quantised point rather than per pixel or per drop — otherwise geometry, carve and rain gate disagree by up to 0.4 of boost at a storm's edge. The 8g-b squall-band rung measured what the quantisation actually costs against the failure mode it is confused with: **max 0.20 / mean 0.015 of a 3600 m wall, against 0.77 / 0.51 for a wrong-frame control.** The frames agree; the quantisation is noise beside a frame error. The stated residual is that agreement is **per-cell, not per-fragment** — a jittered sub-puff's fragments can straddle a neighbouring cell — and, within one puff, the fragment's `z` is its own altitude rather than the puff centre's, so the pattern shears by `|dO/dz| × puff radius` (up to ~250 m near the anvil at `SHEAR_LEAN_S = 600`).

**The GPU never evaluates the wind profile.** `pow`/`sin`/`cos` differ from libm, so the CPU bakes `O(z)` into an 8-entry altitude table per build and both sides read it with `lerpExact`, the one explicit `a + (b − a)·t` formula spelled identically on both sides — GLSL `mix()` would round differently. The table's inputs come from the *pure* profile path (`SSAtmoEnvApplier::windProfileAt(track, phase)` and the **authored** dome height), never `cirrusAltitudeMetres()`, which reads a per-client setting and the live deck.

**Blend vectors, never headings.** When blending between two sampled band winds, lerp the vectors — bearing lerp is undefined at the wrap.

**Transforms that are DISPLAY-ONLY and must never enter the field's coordinates:**

- **The far-field squash.** `SS_SQUASH_CAP_FRAC = 0.98` of `MAX_FAR_CLIP` is where drawn depth tops out, just short of the projection far plane so nothing rasterises against it; the knee sits at 0.8 of the cap, and between them the whole remaining field is folded into the last fifth of drawn depth. It is **shared with lightning and with water** so bolt, cloud and ocean agree about drawn depth. The fold scales each quad corner about the camera, so angular size is preserved and the fragment stage inverts it exactly — which is precisely why it is display-only: nothing in the field's air-frame coordinates may be derived from a squashed position. Two corollaries with teeth: every debug mark goes through the same `squashScale()`, and **lines are subdivided *before* they are squashed** because the squash is not linear along a segment (the funnel's collar stack subdivides before `squashScale` for the same reason); and `mEffRadius` (raised 12000 → 14000 for the veil's reach) is a *drawn-radius* parameter, not a field radius.
- **The virga skew.** Applied *after* the visibility decision, which is why `SSVirga::SKEW_CAP_M` was deliberately **deleted** from `SSDeckLod::WALK_PAD_M` in the 8e-b review: a skewed card from an invisible candidate never draws, so the pad owes it nothing, and a pad term no drawable pixel depends on that also feeds a budget denominator is negative value (lesson 36).
- **The curvature drop**, as specified for the deck's vertex stage — deleted by 8c (§8). At 14 km the drop is 13 m; curvature only matters past ~50 km, which is the shell's own domain and analytic there. Recorded here so nobody adds a geometric curvature term to the deck's vertices believing 8c wanted one.

`WALK_PAD_M` itself is the sum of the LOCKSTEP constants the cores already own — `SHEAR_CAP_M + HERO_SHIFT_CAP_M + 0.4 × CELL_M` — never a hand-tuned literal, and lesson 32 attaches: **a membership pad is only real if the ITERATION reaches it.** The pad widened the disc test for four phases while the square walk bound never grew; a test must show the padded cell being visited, not the constant being summed.

Water's own fold takes the same shape for a different reason and is worth stating because it is the one place the discipline is 3-D: the fold is **radial in full 3D** because the far plane clips *view* depth, so a horizontal-only fold would leave the slant distance alone; every vertex keeps its true ray, direction is preserved, and no triangle crosses the far plane because a sliced triangle rasterises black.

## 4. The core / shell / twin discipline

**Every new deterministic mechanic is a core header**, `indra/newview/ss<name>core.h`. A core includes `lldefs.h` (→ `stdtypes.h`), other `ss*core.h`, `<cmath>` and `<cstdint>`, and nothing else. It may use `llclamp`/`llmin`/`llmax`, `std::lerp` (which *is* the viewer's `lerp`, C++20) and `(S32)floor(f)` (which *is* 64-bit `llfloor`). It contains plain structs of `F32`/`S32`/`U32` and free functions: no LL classes, no singletons, no `gSavedSettings`, no I/O. **`llmath.h` is off limits in cores** — it drags `llsimdmath → llmemory → llerror → boost`, proven by the harness. There is exactly one documented exception in the tree, `<algorithm>` for `std::sort` in `ssstormcellcore.h`, explicitly allowed by the phase-2b brief and marked as such at the include. Because a core cannot include `LLMath`, `SSAirlight::Col3` stands in for `LLColor3`/`vec3` at the core boundary, with its component operations spelled to match GLSL's per-component semantics **in the same order the shaders write them**, because that is what makes the twin's equality bit-for-bit rather than approximate.

The **shell** (`ss<name>.cpp`, the existing singletons) adapts `LLVector*`, settings and tracks, and calls the core. That division is not a preference, it is what makes agent verification possible without a viewer build: scratch tests include cores directly and compile in seconds against `indra/llcommon` + `indra/newview`.

**The ONE FORMULA SITE rule.** Formulas live in cores. Shells and shaders **transliterate** them; they do not re-derive them. Lesson 2 states the boundary: if a shell computes anything numeric beyond unit conversion or LL-type adaptation, the formula moves into a core — and lesson 20 extends it to geometry layout (card slabs, stacks, spans are numeric shell code and move into the core so a twin can integrate the shader's alpha across the seams). Lesson 22 states how to do the move: when a review flags pre-existing shell arithmetic, **refactor all copies in the same pass and pin the refactor bit-identical with a transliteration twin of the OLD text** — the twin is what makes a "no behaviour change" refactor a fact rather than a claim. `ssdeckshadecore.h` is the canonical instance: the deck's structural shading block had been spelled three times in `ssvolcloud.cpp` (veil, fine puff, Tier B body); it now lives once, verbatim from the fine-puff copy, with `deckshadecore.cpp` pinning 144,000 grid points bit-identical to the old fine/macro block and the veil within 1e-6 (measured 0). `ssdaycyclecore.h` is the same move for `dayCyclePhaseAt` and its inverse.

The named authorities today, and each owns its subject outright: `ssatmonoisecore.h` (the one hash every cross-client-synced pattern rides on — change nothing there without updating the golden pins), `ssairlightcore.h` (beam extinction, path transmittance, airlight over a path, and the atmospheric soft clip), `ssdeckshadecore.h` (facing, exponential shade, beam gate, rim ease, buried depth), `ssveilcore.h` (the veil law), `ssdeckframecore.h` (`S`, `O(z)`, `placeWorld`, `frameAir`), `ssdecknoisecore.h` (the de-tile), `ssdecklodcore.h` (camera-only LOD), `ssdeckmacrocore.h` (Tier B), `ssdeckboilcore.h` (the animation integrals), `ssdaycyclecore.h` (the one clock map and its one inverse), `ssinfolookcore.h` (the look pass), `sswindprofilecore.h`, `ssstormcellcore.h`, `ssstormcouplecore.h`, `sssquallcore.h`, `ssvirgacore.h`, `ssvortexcore.h`, `ssatmoinfoviewcore.h`. Constants that mirror a value owned elsewhere are marked `LOCKSTEP` at the declaration with the file that owns them, and **replicated constants change in lockstep or not at all**.

**A comment may claim a property only when a named test demonstrates it.** This is lesson 1, from three phase-1 shell comments that asserted "renders exactly as before" and "every client seeds the same" with nothing behind them. A comment may claim behaviour preservation, bit-identity or cross-client agreement **only** if a named harness test shows it; otherwise it states the actual behaviour. Lesson 39 adds the sharper version for geometry: a *text* pin proves the shader says what the test says, not that either is right — every geometric pairing gets a one-line statement of **why** in words and, where possible, a semantic check beside the text pin. (The 8e-c triplanar bug is the case: the weights were paired with the planes that *contain* the axis instead of the planes that *vary* across the card, and a text pin had pinned the wrong pairing verbatim.)

**The ladder.** Rungs are identified by file-name prefix in `V:\Scratch\atmo\tests`, and `test.js`'s `rungOf` defaults anything unprefixed to `unit`:

| rung | prefix | what it is |
|---|---|---|
| 1 unit | `<core>.cpp`, `unit_*` | invariants from the contract comments, golden pins (seed `0x5EED1337`) |
| — contracts | `contracts_*` | the contract header compiles and its declared API exists |
| 2 scenario | `scenario_*` | compose several cores through a simulated day; two clients at 30 and 144 fps and different login times, same wall clock, bit-identical positional outputs |
| 3 cross-section | `xsection_*` | two or more cores asserted to AGREE (heading convention, lattice incommensurability, shared constants, frame rules) |
| 4 twin | `twin_*` | GLSL transliterated to C++ beside the core formula, equality over a grid |
| 5 visual | `visual_*` | core outputs rendered to `out/*.ppm` so a human can look; no oracle, they exist to be looked at |
| — smoke | `smoke_*` | the include path itself |

**Every rung that could be a tautology carries a failing control.** Lesson 19: a "camera-only" scenario must model the camera-dependent part of the pipeline with two cameras and include a control that fails, or it proves nothing (6c's fed both cameras one candidate set). Lesson 25: stubbed inputs must vary along the axis the finding lives on — a veering wind, a two-keyframe cue. Lesson 26: a rank-dependent path cannot be pinned by one seed; sweep seeds along the rank axis with the old selection rule as the control. Lesson 45: when both sides of a check derive from the same value the check is an identity, so a ladder must inject a non-trivial value somewhere. The controls actually in the tree are the pattern to copy — `SSVeil::veilAlphaOld`, the two-ring sheet emission, the index-based trim, abutting cards, the per-axis jitter, the old hero rule, the old occupancy constants.

Three more rules about what a twin must reach. Lesson 8: **twin the CALL SITE, not just the function** — a byte-identical function pair still diverges when the two sides feed it different arguments, sample at different points, or gate the call differently, so every twin also transliterates the shader's argument construction, sample point and enclosing branch. Lesson 15: **twin the LAST line of the chain**, the alpha or colour assignment, not just the factors; a correct mask multiplied by one forgotten ramp is still wrong. Lesson 9: **any predicate that duplicates a cull or gate condition must be the same core function** — two predicates that agree only in the plane are how a 2-D distance test against a 3-D cull deleted the overshooting top across the near field.

For what the harness structurally cannot see, two rules stand in. Lesson 14: **a render pass the harness cannot see needs a "does anything draw" checklist in the review prompt** — cull state, winding by worked example, colormask, depth mode, and one sibling pass named as the idiom to match. (Phase 5's funnel never drew: back-facing winding under the pass's cull state with no `LLGLDisable(GL_CULL_FACE)`, which every sibling pass has.) Lesson 27: **an accessor exposed beyond the frame that populates its inputs must read CAPTURED values, never borrowed pointers**, and any shell method a reviewer can only read gets a "safe at any time?" question.

**Where tests live, and who runs them.** Tests and verifiers live in the harness, never in the viewer tree. Lesson 35 splits the running: **the full suite is the user's gate, the impacted set is the agent's loop** — a filter derived from the include closure (`--changed`, `--for <header>`), not from a guess. **Agents never run cmake and never build the viewer**; build ownership is the user's, and the phase gates are their builds.

There are **two harnesses against one repo**: `V:\Scratch\atmo` (78 test files, the main ladder) and `V:\Scratch\flow` (12 files, run with `SS_FLOW_REPO=D:\soapstorm`), which is the oracle for the four flow-ported files and where `twin_lightvariant` — the pin that holds `SSAtmoCloudLightVariant` 0 bit-identical over 58k input combinations — actually lives. Section 10 records that this contradicts PLAN §5's "Tests only under `V:\Scratch\atmo\tests`".

## 5. Time and determinism

**One clock (user's rule, 2026-09-06, phase 7e).** Storm **state** — births, ages, positions, forced cues, funnel life — runs on cycle time `tau = utc − dayOffset`, an asset constant plus a shared clock, identical on every client. **Animation** — puff boil, funnel spin, debris, lightning, sound — runs on the wall clock. `phaseAt` and `wallTimeAtPhase` are ONE map and ONE inverse applied to `tau`, both in `ssdaycyclecore.h` and pinned bit-identical to the old track bodies. The editor preview substitutes the **clock** (`tau_ref` latched from the previewed phase, time still flowing), never a second phase map: lesson 31 states it as **when a system must be re-based to a timeline, re-base the clock it consumes, not the map it reads with**, and lesson 34 closes the loophole — **two derivations of one clock are two clocks**; one helper, called by every route, mutable-latched if a const route needs it. Storm durations stay in wall seconds because `tau` ticks at wall rate, so wind in m/s stays honest.

**What is hashed and what is accumulated.** Everything positional is hashed and closed-form: cell identity, birth instant, lifetime, pass side, the funnel's contact offset, keep decisions, jitter, radii, epoch selection. There is **no runtime RNG** anywhere in the sim — note that `LLPerlinNoise` seeds from `rand()` and is *not* reproducible across clients, which is why the fork carries its own hash-based noise. The only accumulators in the whole system are the air-frame drift and the two animation integrals in `SSDeckBoil`. Lesson 13 governs both: **accumulate in F64.** A per-frame F32 sum of `v·dt` diverges about 200 m/h between 30 and 144 fps; the same sum in F64 is millimetres. Measured over an hour at 30 vs 144 fps: **233.75 m in F32, 0.0000005 m in F64.** Any accumulator that positions content is F64 internally and F32 only at the boundary.

**The boil-clock finding, and the rule it produced (fourth build report, D1 + D3; `V:\Scratch\atmo\BUILD_CHECKLIST.md` §10).** `ssVolCloudF.glsl` computed the advected octave's phase as `turn = ss_time × SS_OCT_LAPS × ss_drift_rate × (SS_OCT_DRIFT_FLOOR + ss_churn) × 2π` — a **rate multiplied by an absolute clock**. Both factors of that rate vary with time, and the day-cycle phase they come from derives from `time(nullptr)`, which is **whole seconds**. So the rate was a staircase with a 1 Hz tread, and `phase = rate × t` turned every tread into a jump proportional to *uptime*: 0.0547 laps skipped in one frame after an hour, **0.2156 laps — a quarter of the whole cycle — after four hours**, which is 974× the correct per-frame advance. The same multiplication made the apparent rate `rate + t · d(rate)/dt`, whose second term grows without bound with uptime — the "far too exaggerated" half of the same report. The intermittent hollowing was the identical bug delivered in quarter-cycle jumps: the advected octave is a signed ±0.72 of density on a puff's thickest part, and the worst puff in a 96-puff sweep lost 56% of its core at particular phases, which is why it was a minority of puffs and could not be reproduced on demand.

**The rule, stated once (`ssdeckboilcore.h`): a time-varying rate is INTEGRATED, never multiplied by an absolute clock.** A step in the rate then changes only the *derivative* of the animation, which is invisible; multiplied by `t` it changes the *value*, which is a jump. `advanceLaps` and `advanceFallM` are that integral, F64 internally and F32 at the uniform boundary, with `MAX_DT_S = 0.2 s` capping any hitch, alt-tab or teleport that would otherwise be integrated whole. Max alpha change per frame went from 0.0157 to 0.000057. The rate was also slowed five-fold in the same pass — `LAPS_PER_S` 0.06 → **0.012**, so a full advection cycle takes 66.7 s at maximum convection and 333 s in dead calm (`DRIFT_FLOOR` 0.25; `FALL_MPS` 6.0) — against the user's target of "very slow change to a cloud's appearance". The rain shaft's fall coordinate had the identical shape and is fixed the same way.

**The camera may never select or rank world state.** Rank by hashed id, cull by radius; no "nearest N cells", because two clients 6 km apart would render different skies. The camera affects LOD and nothing else. Corollary rules: time-discretised effects use **wall-clock buckets with a smoothstep crossfade between adjacent buckets** (the `sslightning.cpp:428` idiom), never frame counters and never a raw step; the eased `SSAtmoMagic::mWind` is Euler-integrated per frame and **must never feed anything positional** (feel-only consumers — audio, particles, flexi — keep it); a budget trim over a camera-bounded set is a **stable per-element hash threshold**, never an index or a rank (lesson 18 — an index trim re-picked all 64 curtains on every count change; measured Jaccard 0.00 against 0.69), with `SSVirga::hardCap` the single stated exception, a rank cut on a *fixed* per-cell key that moves at most one cell when the kept set grows or shrinks by one. Lesson 29: **anything the author places by hand must be guaranteed, not hashed** — hashed windows are for the background population. Lesson 42: **a constant borrowed from another system is a coupling** — a system that is "composed like X" gets its own named constants from the start (the squall line borrowed `HERO_SPAWN_MIN/MAX_M` and the 30 km hero cap then spawned every line outside the field).

**Lattice incommensurability is a determinism constraint, not a tuning choice.** `SSStormCell::LATTICE_M = 2900` is deliberately not a whole multiple of `CELL_M` 260, the 2080 m noise tile, `SS_NOISE_M` 880 or `SS_SKEW_M` 1400, nor they of it; the shortest shared period is 37,700 m, beyond a visible field, and folding it into the 800800 m wrap span passes `WRAP_MAX_M` so `lcmSpanM` drops it. `xsection_wind_storm` pins both halves.

**Honest residuals, stated so nobody re-discovers them as bugs.** The drift accumulator is session-start seeded. A wrap keeps the *tiling textures* put but the cell-index hash is not periodic, so the gate and cluster noise still re-roll at a wrap; the rotated second de-tile lattice cannot be aligned by the wrap at all. The camera's altitude band selects which *track's* storm world is observed, exactly as it selects the sky, and each track's world is a pure function of that track's cube. A client whose precip LOD dial zeroes the `TIER_SHEETS` radius sees no rain shafts — a per-client on/off by design of the shared-radius handoff. And per-cell lockstep is not per-fragment lockstep (§3).

## 6. Rendering and composition rules

**Read `doc/viewer/glow_and_alpha.md` before any rendering change.** Its rule is the fork's rendering constitution and its companion `doc/render_glow_pipeline.md` states the standard: "if it disagrees with intuition, the code wins".

**Alpha means different things at different stages, and this is the #1 recurring bug source.** From the moment `mRT->screen` is bound at deferred soften until tonemap, its alpha channel is **not coverage — it is the bloom mask**. `pipeline.cpp:8192` forces `GLOW_MIN_LUMINANCE = 9999`, which zeroes the luminance and warmth terms in `glowExtractF.glsl`, so the bright-pass is pure alpha readback: **glow seed = tonemapped rgb × screen alpha. Nothing else. Ever.** Brightness never blooms. G-buffer alpha can *never* bloom — att0's alpha is the legacy fullbright/emissive mix (so never put coverage there; use discard for cutouts), att1 is glossiness, att2 is a float flag code, att3 carries the sky/cloud/celestial blend weights and is consumed before soften. Impostors, by contrast, carry a real coverage mask. **Alpha-is-glow reasoning is valid only in post-deferred screen passes; sky-pass and G-buffer alpha are ordinary alpha.**

The blend mode completes the model: **additive** passes accumulate alpha linearly (lightning blooms by design), **alpha-blended** passes contribute only `a²` (so rain never visibly blooms), and **masked** passes contribute zero — which is why the puffs' mask is load-bearing, since their near-1 core alphas would bloom hard under alpha blending. The default post-deferred state is `setColorMask(true, false)` — **alpha writes are OFF and you must opt in.** A pass that wants transparency keeps them off and lets `frag_color.a` be coverage (blend still reads SRC_ALPHA); a pass that wants bloom turns them on and treats `frag_color.a` as glow *strength*, sized independently of opacity, because **more bloom is more alpha, not brighter rgb** — the glow seed is tonemap-clamped.

The procedure is mandatory: **before touching any pass, name three things — which target it writes, the blend func, and the colormask — then derive what alpha means there.** And the named antipattern: **never relocate a pass to chase an artifact.** Every historical glow bug was "fixed" by moving a pass somewhere else, trading one alpha side-effect for another because the real variable was never pinned down. Its sibling rule, from the same session: before diagnosing any rendering artifact from a screenshot, establish which shader actually ran — a "misaligned occlusion" was once diagnosed and fixed in a shader whose gate was closed in that frame.

**The sky forward pass is where dark things draw.** The funnel and the veil draw there with **real alpha**, never post-deferred additive, because a dark funnel that writes additive alpha *blooms*.

**Where an overlay or a dim must draw — lesson 52, learned twice.** "The 3-D pass" is not one place. **Anything that dims or overlays the final image belongs AFTER tonemap and exposure, where HUD geometry draws; anything drawn into the HDR scene buffer is measured by auto-exposure.** The info view's one draw site is `render_ui()` in `llviewerdisplay.cpp`, **after `gPipeline.renderFinalize()` and before `render_hud_attachments()`** — post-tonemap, still a 3-D pass, still the world camera, landing in the default framebuffer in display space so nothing feeds back into exposure. Two earlier homes were wrong for two different reasons, and both are recorded so neither is tried again: `SSAtmoDimView::draw()` in the **UI stage** (a 3-D layer re-entering from the UI pass clipped console text and threw the visualisations into the window corners — lesson 48: **the UI stage draws 2-D only; a world-space layer belongs in the 3-D pass, and "on top of the dim" is achieved by drawing the dim in the 3-D pass first**), and `LLPipeline::renderDebug`, which runs inside `renderGeomPostDeferred` and so put the dim into the HDR screen buffer *before* `generateLuminance`/tonemap: a 0.55 linear tint read as roughly 0.30 perceptually **and** auto-exposure then opened up to cancel it over about a second, pumping the whole scene. A post-`renderFinalize` 3-D pass owes the `render_hud_attachments` matrix discipline: push both `gGL` stacks and save the cached copies, `setup3DRender()`, clear `gGLLastMatrix`, bind a shader (`renderFinalize` leaves none bound), and restore viewport, matrices and the `get_current_*` cache on the way out.

**`renderDebug` re-enters from `render_hud_attachments`**, so every Atmo block inside it carries `!hud_only`, exactly as the stock blocks do; an unguarded block draws its world geometry a second time under the HUD's ortho matrices.

**The airlight composition, and its single authority.** The deck is not shaded by a model of its own: `ssVolCloudV.glsl` declares the same nine windlight uniforms the sky runs on and composes `vary_ss_sunlit`/`vary_ss_amblit` following, in its own comment, "cloudsV's exact composition". The airlight ships **separately** as `additiveColorBelowCloud × (1 − combined_haze)` and is added **after every cloud multiplier**, and the reason is recorded at the declaration: folded into the ambient it was multiplied by the storm gloom and the wrap mids, which stripped the warm dawn air off the deck — cold navy puffs under a pink cirrus band — and left the deck meeting the horizon band about 35% darker than the band it joins. Added at the end, deck and dome band converge on the **same pure airlight at the rim**, and the handoff is exact by construction. So the sky, the cirrus band and the deck already agree by design; what they did not share was a single *spelling* of that agreement, transliterated in `skyV.glsl`, `cloudsV.glsl` and `ssVolCloudV.glsl`, with 8c's shell about to be a fourth. **`ssairlightcore.h` is now the single authority** for the beam's extinction to a given elevation, the transmittance over a view path, the airlight that path has gathered, and the soft-clip response every cloud surface should end on. What it deliberately does *not* own is stated in the header: the haze glow's angular term (genuinely per-site — the dome reads it along the true ray under the horizon mirror, the band along the possibly-mirrored `rel_pos_norm`, the deck caps it at `SS_GLOW_CONE_CAP`), the sun/moon selection, the horizon-band share, the disc-floored elevation and the ray's own mirroring, all of which stay at the call site.

**The bloom-safety constraint that governs the cloud bound.** The deck's output must stay inside exactly the range the old hard clamp occupied, so the bright-pass sees nothing new — this is the constraint, and everything else about the ending is negotiable. The shader used to end on `clamp(body + airlight, 0, 1) * 2.0`, which was introduced because HDR rgb cannot bloom but unclamped colour still blows out the tonemapper, and the un-bounded version produced "a halo around every puff". The clamp then caused its own defect: **a hard clamp has zero derivative above 1**, so on a representative bright daylight set 121/121 inputs saturated and 558 of 726 lighting-variant pairs landed on the same 8-bit pixel — the A/B dial did nothing in daylight. It is now `ss_soft_clip_unit`, transliterated from `SSAirlight::softClipUnit` and pinned bit-identical over 1728 colours by `twin_deck_softclip`: the compression half of `PBRNeutralToneMapping` (Khronos Neutral, the tonemapper every non-sky pixel already passes through), with `SOFT_CLIP_KNEE = 0.8 − 0.04 = 0.76` and `SOFT_CLIP_DESAT = 0.15`. It is the identity below the knee, C1 at the join, strictly increasing everywhere so no input range is flattened, and **strictly under 1 for every finite input** — which is what keeps the following `× 2.0` inside exactly the range the clamp occupied. **Bloom safety holds by construction.** It is also hue-preserving where the clamp was not: `(4.0, 1.2, 0.6)` clamped to `(1.000, 1.000, 0.600)`, red and green equal and the hue destroyed; the curve gives `(0.983, 0.510, 0.408)`. Variant separation went from 168 of 726 distinguishable pairs to 242.

**The lighting-variant rule.** Every step of the dimensionality ladder extends `SSAtmoCloudLightVariant`; **none of them changes variant 0.** The pristine look stays pinned by `twin_lightvariant` over its 58k input combinations, and each addition stays A/B-able against it in a live build, which is the only place this class of change can be judged.

Two more rules from the lightning pass that generalise. Its fragment ending is the canonical shape for an additive bloom pass — `rgb = min(tint · bright · mask, 3)`, `alpha = glow · bloom_fraction · mask · min(bright, 1)` — brightness above white reaches the tonemapper through the RGBA16F screen target and the bloom seed is never inflated by it. And **immediate mode is banned in a pass whose shader declares `normal`/`tangent`**, because the immediate-mode path reads recycled memory for them; `LLVertexBuffer::unbind()` goes immediately before each `setBuffer`, and `sspreciprenderer.cpp` is explicitly *not* the pattern to copy here — it is correct by accident of sequence, not by construction.

Finally, the ambient hazard: **GL state is manually managed and leaks by convention.** Passes trample blend and colormask and only partially restore. When adding a pass: name your target, blend func and colormask, and restore what the ambient state expects.

## 7. The entity / scheduler split

**The storm cell is the entity's scheduler and lifecycle; the lattice only seeds it** (user, 2026-09-06, third build report item 5, answering a question about whether the cells should become tiles). This is why storm cells stay under an entity-based model even as the deck moves to a container-and-operators model: the cell is not a sample of a field, it is the thing that decides *when* and *where* an entity exists and *how old* it is. What gets drawn is a separate question, answered by the operators of §2 and, when 8b lands, by the anatomy tier's parts.

`SSStormCell` is a POD **recomputed from scratch every frame**: every function is a pure function of (shared seed, cycle time, lattice/world position, the weather the *shell* evaluated at the candidate's birth time). No persisted sim state, no `dt`, no camera, no frame counter. A client joining mid-storm recomputes the identical cell from its birth phase. Positions are world-frame, never the drifted air frame.

The **shell owns anything that needs a weather cube, a region or a setting**: it enumerates lattice cells with the core, asks the core for each candidate, evaluates the cube at the candidate's birth time, gates it, ranks survivors **by hashed id**, and composes the hero flyby against the weather domain's anchor. That enumerate/gate/rank/hero pipeline is itself a core template (`resolveActive`) so it sits inside the harness rather than outside it — the 2b hardening moved it there after the audit found the shell re-spelling the day-phase fmod and holding the whole pipeline where no test could reach.

**Slot filling is anchor-relative, never camera-relative.** `SSStormCouple::MAX_CELLS = 4` uniform slots face 20–40 alive cells at severe weather; slots go hero-first and then by distance to the weather-domain **anchor** — shared world state, so every client under the sky fills the same slots — with `selectSlots` callable from the shell so neither side re-derives the rule. The anchor is the region whose environment asset is driving, never the camera. The cells that matter around the region shape the deck; the deck-wide consolidation ramp covers the rest.

**The hero is staged, not emergent.** A severe event that plays out offscreen might as well never have happened, so tornado/supercell spectacle is a **composed flyby, one at a time**: closest approach at `HERO_CLOSEST_AGE01` 0.5 whatever the wind, spawn distance `|motion| × 0.5 × lifetime` clamped to `HERO_SPAWN_MIN/MAX_M` (200 m – 30 km) up the *deviated* storm-motion vector, and the closest approach measured on the **funnel's contact point, not the cell centre**. The hero is cull-exempt and may be born outside the 12 km field. Background cells provide sky texture and never carry the tornado. The calibration constants behind this, all moved in the 7f pass after a probe found every hero arriving at age 0.07–0.09 with intensity 0.00–0.12: `LIFE_MIN_S` 1200 / `LIFE_MAX_S` 4200, `SPAWN_THRESHOLD` 0.245, `INTENSITY_FULL_SCORE` **0.65** (was 1.0, which mapped typical scores of 0.3–0.5 onto intensity 0.0–0.15 so every storm was weak), `HERO_INTENSITY_MIN` 0.7, `MESO_TORNADO_MIN` **0.35**. Lesson 40 is the rule that came out of it: **when a test has to hunt for a fixture that makes a gate pass, the gate is the finding** — record the search as a calibration failure and do not ship the lucky anchor. Lesson 53 is its twin: **a spawn test must assert what the spawn drives**; "it spawned" at intensity 0 is the same as not spawning.

**Vortices are children, not peers.** Everything about a vortex is a pure function of (seed, parent id, slot, clock) plus the parent's live state the shell already resolves. Multi-vortex structure is a **shader-side angular term** (`radius(θ,t) = base·(1 + amp·sin(Nθ + ωt))`), never extra entities, and it is spent as a **radial alpha mask** so the silhouette actually lobes — never as a brightness multiply, which flattens half the waveform and leaves a fixed-width card. `MAX_ACTIVE` 3, `COLLARS` 14, `SLOTS_PER_CELL` 2. Dust devils are parentless, on their own small lattice with their own seed, anchor and clock, above the cells gate so the Interest cost gate cannot starve them on clear dry days.

**Composition removes independence.** A squall line is a **spawn template**, not a new code path: a rare lattice-epoch event that emits ordinary candidates along a line sharing one birth and one motion. A forced storm is an ordinary candidate with pinned birth parameters. Lesson 47 states the invariant: **a member of a composed group moves with the group** — per-member deviation is a property of *free* cells, and composition removes it. Line members are never the hero (an embedded supercell is tornado-eligible and was being composed away from its own line), and a live line suppresses the spontaneous hero search while an authored hero still wins. Authored events carry a weather floor — `AUTHORED_FLOOR_MOISTURE` and `AUTHORED_FLOOR_CONVECTION` both 0.85, with a `static_assert` that the product clears `INTENSITY_FULL_SCORE` — because the generator deliberately writes a dry pre-cue sky and without the floor every member gated out and the wall arrived and did nothing.

**Why the anatomy tier is an entity extension and not a finer field** (lesson 50): the volumetric field is a one-layer height field per 260 m cell, and a cumulonimbus is a multi-layer *shape*. **When a per-cell scalar system is asked for a multi-layer shape, add a level of abstraction — an entity with parts — do not bend the scalars.** The field stays the fabric for stratiform and fair-weather decks; entities own the organised structures, emit their own puffs into the same deck, same sort, same shader, same budget, and carve the field's inputs analytically so gate, bake and precip agree without noise reads.

**Every entity class that ships gets a view, or a layer in one, before its phase closes**, and the rule is written into the phase's review. The anatomy tier is explicitly *not* an extension of V2; it gets its own V6.

## 9. House conventions

**Naming.** Fork files take the `ss` prefix in `indra/newview` and are registered in `CMakeLists.txt` beside the `fsrezqueue` entries. New **identifiers** — settings, classes, constants — take the `SS` prefix, **never `FS`**; `FS`/`fs` names are reserved for inherited Firestorm code. Settings cluster into families: `SSAtmo*` for the weather system (203 keys in `settings.xml` today — `SSAtmoEnabled`, `SSAtmoCloud*`, `SSAtmoInfoView*`, `SSAtmoLightning*`, `SSAtmoSnow*`, `SSAtmoWhiteout*`, `SSAtmoWindFlow*`), plus `SSWorldField*`, `SSHUDSupersample`, `SSBC7*`, `SSROC*`. **A setting must be a real `settings.xml` entry, not a lazy `LLCachedControl`** — a control that an `LLCachedControl` declares for itself gets no `Persist` flag and did not exist until it was used. Windows' `windef.h` macros `NEAR`/`FAR` **and lowercase `near`/`far`** are landmines: never use them as identifiers, variables or lambda names.

**Comments.** `ss*` sources carry the viewerlgpl licence block, a one-line `@brief`, one `//` line above every function in the `.cpp` (why and what, not how), and inline `// <SS:Nexii> …` comments as **single long lines** where rationale is load-bearing — usually ending with a `[interaction: X]` tag or a `doc/…md` pointer. Multi-line essays are out; the design story goes in `doc/atmo_magic_*.md`. In stock files, keep `<SS:Nexii>` to about three long lines with a doc pointer, wrap injections in the tags, and **never reformat stock viewer or Firestorm comments**. The `[interaction: X]` tags at cross-system read sites are **the ground truth for blast radius** — the archived interaction map may have drifted, the tags have not.

**XUI.** To make a widget stretch with its parent, give it explicit **`left` and `right`** (no `width`) plus `follows="…|right"`; do **not** keep `left_pad` and merely add `right`, because `ParamValue<LLRect>::updateValueFromBlock` only takes the "prefer explicit left and right" branch when *both* are provided, and `LLView::applyXUILayout` clears `rect.left` whenever a `left_delta` (which is what `left_pad` becomes) is in play. Negative `right`/`bottom` are measured from the parent's far edge; positive `bottom` under `layout="topleft"` measures down from the parent's top. When re-anchoring an existing row, express the new `right` as `−(parent_width − current_right)` so load-time geometry is unchanged and only the follows flags decide resize behaviour. Each tab is a `scroll_container` wrapping a fixed-height content panel so the floater can be resizable and a tall tab scrolls instead of being cut off. Because every control binds through `control_name`, relocating a row between panels is XML-only — the floater reaches everything through recursive name-based `getChild`.

**Where things are recorded.** Design decisions, rationale and rejected alternatives live in `doc/atmo_magic_*.md`. The verified map of the stock viewer lives in `doc/viewer/` — read `index.md` first, and `glow_and_alpha.md` before touching a pass. Out-of-date design and build logs live in `doc/archive/` and are good for **intent only**. **Work state** — phases, outcomes, what is in flight, the numbered lesson list — lives in `V:\Scratch\atmo\PLAN.md`, and the judging list for the next build in `V:\Scratch\atmo\BUILD_CHECKLIST.md`. Neither is in the repo, and that is deliberate: tests and verifiers live in the harness, never in the viewer tree.

**Working conventions.** Work happens on `feature-*` branches, merged to master by PR. Agents never run `cmake` and never build the viewer; the user builds and does visual sign-off at phase gates. Agents never run git write commands, and must never assume the working tree is theirs alone — the user has committed mid-run. Patch scripts go through a file write and then `python file` (heredocs with quotes break in the shell wrapper); workflow scripts are pure ASCII with LF endings and must contain no backticks inside an agent prompt; `build.ps1` needs `powershell -ExecutionPolicy Bypass -File` on this machine. Model policy is per `agent()` call, never per phase declaration (lesson 6), and one agent takes one file-ownership slice under about 40 tool calls (lesson 38) — long sidechains are where half-applied edits and refusals live, and a recovery prompt starts with an inventory of the tree, never a re-run of the original list.

### 9a. Rain vocabulary - five different things, named once

Established 2026-09-07 after the orchestrator briefed an agent on the wrong one. "Raindrops" has meant five
distinct systems in this fork, and the two most easily confused have **opposite** correct behaviour, so the names
below are the required vocabulary in prompts, comments and reports.

| name | what it is | pass / owner | the invariance it must satisfy |
|---|---|---|---|
| **Lens drops** | drops on the camera itself, as though on a lens or a visor | `ssPostLensF.glsl`, post-process, laws in `ssscreenfxcore.h` | fixed in SCREEN space. A drop does not move when the camera turns, rolls, or the wind veers. Only its run-down trail follows the slide direction. |
| **Surface drops** | drops on opaque world geometry | `ssSurfaceWetF.glsl`, a screen-space pass over the G-buffer, called from `pipeline.cpp` inside the deferred lighting phase | fixed in WORLD space. The pattern at a given world point does not change when the camera moves at all. |
| **Glass drops** | drops on alpha-BLENDED surfaces | does not exist; structurally unreachable from the G-buffer pass, since blended geometry draws later through `LLDrawPoolAlpha` and never writes the G-buffer. Design: `doc/atmo_magic_wet_alpha.md` | world-fixed like surface drops, plus two-sided and refracting rather than albedo-tinting |
| **Precipitation particles** | the actual falling rain and snow near the camera | `ssprecipitation.cpp` / `sspreciprenderer.cpp` | world-fixed, wind-advected; hands off to virga at its own tier radius |
| **Virga shafts** | distant rain as fog-like curtains, emitted into the deck's own puff list | `ssvirgacore.h` + the deck's draw | world-fixed; sorts against puffs because it IS a puff |

**State, and which systems may hold it** (user, 2026-09-07). The LENS is stateful: one surface, always in view, a
bounded drop population, and a real history the viewer never leaves - so accumulation, drops releasing by size, a
running head consuming the fine stipple in its path and growing as it does, and medium beads pinched off into the
wake are all simulated, per the reference the user named (tympanus.net/Development/RainEffect). Every WORLD-anchored
drop system is stateless, and for a correctness reason rather than a cost one: a surface streams into view already
wet, so a per-surface simulation could only pop in empty and fill up while you watch, or fabricate an arbitrary
warm start. A stateless law keyed on world position has the pattern there the instant the surface appears, with
nothing to seed, evict or clear across teleports and region crossings. The division that follows is the rule: HOW
WET a surface is may evolve and be remembered (the world-anchored surface field already owns that, and accumulation
therefore belongs to the wetness scalar, not to a drop list), while WHAT THE DROPS LOOK LIKE at that wetness is a
stateless function of world position, wetness and time. The asymmetry between lens and world is deliberate.

Two consequences worth stating because they have already caused bugs. First, **"the drops move when I move" is a
defect for four of the five and the CORRECT behaviour for none of them in the way it usually gets reported** - for
lens drops the fault is that they move with the camera, for the other four that they move with it too, but the fix
is the opposite in kind: the lens pass must stop consulting a world-derived direction for placement, the others
must stop consulting a screen-derived or camera-derived coordinate. Second, alpha-MASKED geometry does write the
G-buffer, so surface drops already apply to cutout materials; only alpha-BLENDED panes are missing. A report of
"no drops on glass" therefore means blended glass specifically, and a report of "no drops on foliage" would be a
different and more ordinary bug.

## 10. Where the sources disagree, and where code contradicts a stated rule

A contradiction found is worth more than a contradiction silently resolved, so these are recorded rather than fixed. This document does not pick winners.

1. **`reachOut`: placeholder for an annulus, or the permanent inner half of a complement?** `ssveilcore.h` (the `[interaction:]` line in its header) and `doc/atmo_magic_far_clouds.md` (§"Phase 8g outcome — the veil law") both state that the 8c horizon deck's **annulus replaces `reachOut`** when built, and that the veil then goes back to ending at its rim. `doc/atmo_magic_phase8_show.md` §5, rewritten 2026-09-06, **rejected the annulus** and states the opposite: `reachOut` "stops being a stand-in for the annulus's inner kilometres and becomes the permanent inner half of the complement", with `shellReachIn(d) + SSVeil::reachOut(d) == 1` identically. Two files carry the superseded story, one of them a core header.

2. **`ssairlightcore.h` says "NOTHING CALLS THIS YET" and it is no longer true.** The header states that the consolidation lands as a separate step and that "until the rewire, a change here changes nothing on screen". `ssVolCloudF.glsl` already transliterates `SSAirlight::softClipUnit` as `ss_soft_clip_unit`, names the core as "the AUTHORITY here", and is pinned bit-identical by `twin_deck_softclip.cpp`. A change to `SOFT_CLIP_KNEE` or `SOFT_CLIP_DESAT` today changes every deck pixel and breaks a twin. The claim is stale for the soft-clip half of the core and correct for the beam/airlight half. **This is a rule stated and a file that contradicts it.**

3. **`phase8_show.md` §6 item 1 still prescribes the render site that lesson 48 reversed.** It reads "draw the info view's in-world layer from the UI stage, after the dim quad, with the 3-D projection pushed (the HUD-render idiom)". The shipped code draws from `render_ui()` after `renderFinalize` and says so at length in `ssatmoinfoview.cpp`. Item 1 was never updated. **Doc contradicts code; the code is right.**
